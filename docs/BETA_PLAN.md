# Five-tester beta plan

The beta objective is to learn whether KERF's evidence helps technical teams decide if an AI data agent is safe to release. It is not to manufacture impressive user counts.

## Ideal first testers

- One data analyst who regularly writes SQL.
- One analytics or data-engineering student.
- One software engineer who has integrated an LLM API.
- One small-business operator who consumes reports but does not write SQL.
- One product or operations professional who evaluates software quality.

## 30-minute session

1. Ask the tester what would make them trust an AI-generated business answer.
2. Let them inspect three evaluation cases without coaching.
3. Run the fixture suite and explain why it is not a model benchmark.
4. If a live key and budget are available, run one or two models.
5. Ask the tester to find one confusing metric, missing piece of evidence, or unsafe assumption.
6. Record feedback through the product form only with their knowledge.

## Questions

- Could you tell why an answer passed or failed?
- Did the expected SQL and returned rows provide enough evidence?
- Which metric would you use to block a release?
- What did you expect to click that was missing?
- Would a Markdown, CSV, or JSON report help your workflow?
- What would prevent you from trusting this with real company data?

## Evidence to retain

- Tester alias and actual role.
- Session date and tested release.
- Model/provider used, if any.
- Specific observed failure or confusion.
- Product change made in response.
- Consent before using an attributed quote.

Do not add friends as “beta users” unless they actually use the product and provide specific feedback. Do not create testimonials for them.
